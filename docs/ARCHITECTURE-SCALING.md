# NECTRA Architecture & Scaling Guide

## 1. Current Single-Node Architectural Ceiling
NECTRA is designed as an ultra-low latency, single-node application backed by SQLite in Write-Ahead Logging (WAL) mode (`data/nectra.db`).

### SQLite Concurrency Model & Operating Limits
- **Single-Writer Constraint**: SQLite permits strictly one exclusive writer process at any instant. While WAL mode enables concurrent readers (`PRAGMA journal_mode = WAL`), concurrent writes are queued and governed by `PRAGMA busy_timeout = 5000`.
- **Throughput Boundary**: On local NVMe storage, SQLite sustains ~2,000–5,000 write operations/sec. In NECTRA, write transactions are generated by trade fills, balance ledger entries, and audit rows.
- **Process Decoupling**: Release 2 moves bot execution from the web process to a standalone worker (`server/bot-runner.js`) under a dedicated supervisor (`scripts/supervisor.js`).
  - **Web Process (`server/index.js`)**: Serves HTTP APIs, wallet authentication, and admin management.
  - **Bot Runner (`server/bot-runner.js`)**: Runs market evaluations, Jupiter swap executions, and position tracking.
  - **Crash Domain Isolation**: A catastrophic failure (`kill -9`) on the HTTP tier leaves live bots executing uninterrupted.

## 2. Path Off the Ceiling: Migration to Distributed PostgreSQL

When platform scale exceeds a single instance's capacity (multi-node horizontal scaling or cross-region failover), migrate to PostgreSQL following this staged blueprint.

### Architecture Transition Blueprint
```
[ Load Balancer (Nginx / Cloudflare) ]
            |
    +-------+-------+
    |               |
[ Web Node 1 ]   [ Web Node 2 ]   ... [ Web Node N ]
    |               |
    +-------+-------+
            |
[ PgBouncer Connection Pooler ]
            |
    +-------+--------------------+
    | Primary (Read/Write)       |
    | [ PostgreSQL 16+ ]         |
    +-------+--------------------+
            | Streaming WAL
            v
    +----------------------------+
    | Read Replica 1 (Reporting) |
    +----------------------------+
```

### Migration Phases
1. **Schema Mapping & Types**:
   - SQLite `INTEGER PRIMARY KEY` → PostgreSQL `BIGSERIAL PRIMARY KEY` or `UUID`.
   - SQLite `REAL` → PostgreSQL `NUMERIC(20, 8)` to eliminate floating-point representation drift.
   - SQLite JSON strings → PostgreSQL native `JSONB` with GIN indexing for fast querying.
2. **Concurrency Control & Row Locking**:
   - Replace SQLite table-level write locks with PostgreSQL row-level locks:
     ```sql
     SELECT * FROM wallets WHERE id = $1 FOR UPDATE;
     ```
   - Eliminates `SQLITE_BUSY` errors entirely during high-frequency balance updates.
3. **Dedicated Job Queues**:
   - Replace SQLite poll loops (`setInterval`) with a distributed broker (Redis Streams or BullMQ) for trade dispatch and settlement tasks.
4. **Zero-Downtime Data Migration**:
   - Snapshot SQLite with `VACUUM INTO`.
   - Run pgloader / custom ETL into PostgreSQL staging.
   - Cut traffic over to PostgreSQL with connection pooling via PgBouncer.
